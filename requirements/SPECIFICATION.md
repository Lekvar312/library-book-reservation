# Специфікація вимог до системи

**Library Book Reservation System** — вебсистема для пошуку та резервування книг у бібліотеці.

Документ деталізує вимоги з [REQUIREMENTS.MD](REQUIREMENTS.MD) і пов’язаний з [USER_STORIES.md](USER_STORIES.md) та [USE_CASE_DIAGRAM.md](USE_CASE_DIAGRAM.md).

## 1. Ролі

| Роль | Опис |
|------|------|
| Гість | Неавторизований відвідувач. Може переглядати каталог і шукати книги. |
| Користувач | Зареєстрований читач. Може резервувати книги та керувати власними резервуваннями. |
| Бібліотекар | Працівник бібліотеки. Керує каталогом книг і обробляє резервування. |
| Адміністратор | Керує користувачами, ролями, налаштуваннями системи. Має всі права бібліотекаря. |

## 2. Функціональні вимоги

Пріоритети: **M** — обов’язково (Must), **S** — бажано (Should), **C** — за можливості (Could).

| FR-23 | Система повинна автоматично переводити підтверджене резервування в статус «Прострочено», якщо книгу не забрали протягом встановленого терміну (за замовчуванням — 3 дні), і повертати примірник у доступні. | Система | S |
| FR-24 | Після скасування або завершення резервування система повинна повертати примірник у доступні. | Система | M |

## 3. Нефункціональні вимоги

### 3.1. Продуктивність

| ID | Вимога |
|----|--------|
| NFR-01 | Основні сторінки повинні завантажуватися не довше ніж за 2 секунди за нормального навантаження. |
| NFR-02 | Час відповіді API для пошуку та фільтрації не повинен перевищувати 500 мс для каталогу до 10 000 книг. |
| NFR-03 | Система повинна підтримувати щонайменше 100 одночасних користувачів без помітного погіршення роботи. |

### 3.2. Безпека

| ID | Вимога |
|----|--------|
| NFR-04 | Паролі повинні зберігатися лише у вигляді хешу (bcrypt або argon2). |
| NFR-05 | Перевірка прав доступу за роллю повинна виконуватися на сервері для кожного захищеного запиту, а не лише в інтерфейсі. |
| NFR-06 | Уся взаємодія з системою в продакшн-середовищі повинна відбуватися через HTTPS. |
| NFR-07 | Система повинна бути захищена від поширених вразливостей: SQL-ін’єкцій, XSS, CSRF. |
| NFR-08 | Сесія користувача повинна завершуватися після періоду неактивності (за замовчуванням — 24 години). |
| NFR-09 | Система повинна обмежувати кількість невдалих спроб входу (наприклад, 5 спроб за 15 хвилин). |

### 3.3. Надійність і цілісність даних

| ID | Вимога |
|----|--------|
| NFR-10 | Створення резервування та зміна кількості примірників повинні виконуватися атомарно, щоб два користувачі не могли зарезервувати останній примірник одночасно. |
| NFR-11 | Система повинна коректно обробляти помилки та показувати користувачу зрозуміле повідомлення без технічних деталей. |
| NFR-12 | Дані повинні регулярно резервуватися (бекап щонайменше раз на добу). |

### 3.4. Зручність використання

| ID | Вимога |
|----|--------|
| NFR-13 | Інтерфейс повинен бути зрозумілим для користувачів без спеціальної технічної підготовки; резервування книги має займати не більше 3 дій від сторінки книги. |
| NFR-14 | Інтерфейс повинен бути українською мовою. |
| NFR-15 | Інтерфейс повинен відповідати базовим вимогам доступності WCAG 2.1 рівня AA (контраст, підписи полів форм, навігація з клавіатури). |

### 3.5. Сумісність і адаптивність

| ID | Вимога |
|----|--------|
| NFR-16 | Система повинна коректно працювати на ПК, планшетах і мобільних пристроях (ширина екрана від 360 px). |
| NFR-17 | Система повинна підтримувати дві останні версії браузерів Chrome, Firefox, Safari та Edge. |

### 3.6. Супровід

| ID | Вимога |
|----|--------|
| NFR-18 | Код повинен бути написаний на TypeScript і мати єдиний стиль, що перевіряється лінтером. |
| NFR-19 | Ключова бізнес-логіка (резервування, зміна статусів, перевірка прав) повинна бути покрита автоматичними тестами. |
| NFR-20 | Проєкт повинен мати інструкцію із запуску в README. |

## 4. Обмеження

### 4.1. Технічні обмеження

| ID | Обмеження |
|----|-----------|
| C-01 | Застосунок розробляється на фреймворку Nuxt (Vue 3, TypeScript); серверна частина реалізується через серверні маршрути Nuxt (Nitro). |
| C-02 | Система є вебзастосунком; окремі мобільні застосунки не розробляються. |
| C-03 | Для зберігання даних використовується реляційна база даних (наприклад, PostgreSQL або SQLite). |
| C-04 | Система не інтегрується з наявними автоматизованими бібліотечними системами (АБІС) та зовнішніми каталогами. |

### 4.2. Бізнес-обмеження

| ID | Обмеження |
|----|-----------|
| C-05 | Система обслуговує одну бібліотеку (без підтримки мережі філій). |
| C-06 | Система не здійснює онлайн-оплат, штрафів та електронної видачі книг; видача відбувається фізично в бібліотеці. |
| C-07 | Резервувати можна лише книги з наявними вільними примірниками; черга очікування на зайняті книги не передбачена. |

### 4.3. Організаційні та правові обмеження

| ID | Обмеження |
|----|-----------|
| C-08 | Проєкт виконується в межах навчального курсу з обмеженими часом і командою розробників. |
| C-09 | Обробка персональних даних користувачів повинна відповідати Закону України «Про захист персональних даних»: система збирає лише необхідні дані (ім’я, email). |
